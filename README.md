# 知乎 · 回响（Echo in Zhihu）

> 把值得在意的一句话，继续读成一场讨论。

知乎·回响是一款基于知乎内容的片段级讨论发现与连接产品。它用 AI 从长回答中识别三至六个值得展开的见解，检索知乎站内相关内容，让用户沿着具体观点进入有来源、有差异的讨论。

**产品 Demo**：https://zhihu-why.vercel.app/
**GitHub Pages 预览**：https://chelsealeezc.github.io/ZhihuWHY/

## 产品概述

知乎里常常有这样一个阅读时刻：一篇长回答读到一半，其中一句话让人停下来。我们想知道还有谁有过相似经历，也想看看持不同判断的人为什么这样想。但离开当前页面后，用户需要自己概括关键词、重新搜索，再从许多结果中寻找真正相关的表达。

问题不是用户对深内容失去兴趣，而是**兴趣发生得比一篇文章更细**——用户被触动的是一个具体判断、一段真实经历或一个适用条件，现有阅读与推荐却主要以整篇回答为单位。

知乎·回响希望把阅读中的停顿变成入口，让一句在意的话继续生长为一场有来源、有差异的讨论。

### 核心思路

| 设计原则 | 说明 |
|---------|------|
| **从读完变成随时进入** | 连接提前到阅读过程中，用户对某段观点产生兴趣时直接从这个片段进入讨论，不需要先离开原文 |
| **见解是最小连接单位** | 见解不是摘要也不是金句，它包含可以继续展开的问题：一个有分歧的判断、一段有参考价值的经历、一种选择或一个适用条件 |
| **AI 组织讨论，真实内容构成讨论** | AI 负责理解长文、提出核心问题、生成搜索线索并判断候选内容与用户选择的关系；真正进入讨论流的内容来自知乎回答和文章 |
| **一次选择改变接下来看到的内容** | 每条见解提供三至四个观点选项，用户最多选择两项，系统据此对知乎搜索结果进行立场分类和相关度排序 |
| **从观点发现走向真人连接** | 用户从一条具体表达进入作者主页，在有共同兴趣或明确分歧的前提下发起私聊 |

### 产品解决的问题

1. 长回答中的具体兴趣点无法被单独承接，读完或收藏后很难沿着它继续探索
2. 讨论同一件事的回答和文章分散在不同页面，用户看不见内容之间的关系
3. 点赞无法说明用户认同了什么，评论又要求用户先组织完整语言
4. 主题相似不等于观点相近，普通相关推荐很难回应用户刚刚做出的具体选择
5. 用户想理解不同意见或找到同好时，缺少从具体观点自然进入人与人交流的入口

## 产品流程

产品由六个连续环节组成。用户先选择内容来源，在阅读中发现见解，再查看围绕当前问题的知乎表达；提交自己的选择后，系统重新组织相近与不同观点，最后进入讨论空间继续阅读、表达，并找到值得进一步交流的人。

### 1. 内容入口

| 来源 | 需要登录 | 说明 |
|------|---------|------|
| 内置长文 | 否 | 两篇完整知乎长文，无需任何配置即可体验完整流程 |
| 探索知乎 | 否 | 通过服务端 Access Secret 搜索知乎公开内容 |
| 我的收藏 | 是 | 完成 OAuth 后读取用户收藏夹 |
| 我的创作 | 是 | 完成 OAuth 后读取用户创作内容 |

收藏、创作和搜索结果可以一次选择一至五篇并导入；内置长文可直接打开体验。

### 2. 沉浸阅读

阅读页左侧保留完整正文，右侧把长文整理为三至六条「答主的看法」。每条见解包含：
- **短标题**：一句话概括见解主题
- **核心问题**：可以继续展开的讨论方向
- **说明**：为什么这段内容值得停下来
- **观点选项**：三至四个具体看法，用户最多选择两项
- **原文锚点**：点击定位到对应段落，随时回到完整语境

### 3. 观点延伸

系统根据见解对应的搜索词获取知乎回答与文章。内容卡片显示标题、作者、观点片段、赞同信息和关联原因；用户可以快速浏览，也可以打开知乎原文。搜索失败时页面明确显示错误，不把示例内容伪装成真实结果。

### 4. 立场选择

用户最多选择两个更接近自己的观点。提交后，服务端获取最多十条候选内容，由 AI 判断其与当前选择的关系，结果按三组分类：
- **和我相近**：支持用户当前判断的表达
- **和我不同**：强调不同结论或反例的表达
- **立场不明**：证据不足以判断的表达

每条结果都显示简短的分类依据和相关度分值。

### 5. 讨论空间

讨论空间把当前问题、来源文章、相关内容和用户选择放到同一页面。用户可以：
- 在「全部 / 和我相近 / 和我不同 / 立场不明」之间切换
- 对具体表达进行认同、追问或回应
- 写下自己的看法
- 每条真实相关内容保留知乎原文入口

### 6. 找到值得聊聊的人

「值得聊聊的人」来自当前讨论中的相关作者。用户可以看到：
- AI 分身基于答主过往公开表达的立场摘要
- 表达特征和可用的公开表达摘录
- 围绕具体分歧连续追问，或直接私聊相关作者

> AI 观点分身是基于公开片段的观点模拟，不是与原作者建立实时私信，也不代表本人发言。

## 技术方案

### 整体架构

| 层级 | 技术栈 | 职责 |
|------|--------|------|
| 前端 | React 19.1 · React Router 7.8 · Vite 7.1 | 内容选择、阅读、观点选择、个性化结果、讨论空间、主题切换 |
| 服务入口 | Vercel Functions · Node 路由 | OAuth、用户数据、AI 分析、个性化推荐和知乎搜索 |
| AI 服务 | Responses API | 生成见解、立场分类和相关度评分 |
| 知乎数据 | 开放平台 OAuth + 搜索接口 | 读取收藏与创作、搜索公开回答和文章 |
| 内容与状态 | Markdown 内置文章 · localStorage | 离线示例、缓存导入内容、讨论上下文和主题偏好 |

### 两类核心 AI 任务

**内容分析**：接收文章标题、作者和带编号的段落，要求模型以 JSON 返回三至六条见解。服务端校验见解数量、必填字段、三至四个观点选项和原文锚点。

**个性化推荐**：先使用知乎搜索获得最多十条候选内容，再让模型仅依据标题与摘要将内容分为相近、不同和立场不明。模型同时返回分类原因与零至一百的相关度。未被有效分类的内容自动进入立场不明，避免在证据不足时强行判断。

### 知乎内容与用户数据

公开搜索无需用户登录，由服务端使用 Access Secret 调用知乎开放平台。返回内容统一映射为标题、片段、作者、头像、认证说明、赞同数、评论数、知乎排序分值和原文链接。完成 OAuth 后，产品还可以读取用户最近的收藏与创作内容。

### 缓存与体验降级

- 文章分析设置 30 秒超时，成功结果按文章标识在浏览器缓存 24 小时
- 同一页面的重复分析和搜索请求会被合并
- AI 分析失败时使用与内置文章对应的预置见解
- 知乎搜索失败时显示真实错误
- 个性化分类失败时保留原有主题相关内容
- 全站支持浅色和深色主题，主题偏好保存在浏览器

### OAuth 与数据安全

- 生成 24 字节随机 state，有效期 10 分钟，使用 timing-safe equal 校验返回值
- 授权成功后立即消费 state，防止同一回调重复使用
- 部分知乎环境不返回 state 时，只有部署者显式启用兼容开关才会放行
- 会话采用 AES-256-GCM 加密后写入最长 8 小时的 Cookie
- Cookie 设置 HttpOnly、SameSite Lax，生产环境启用 Secure
- AI Key、知乎应用密钥、Access Secret 和 Session Secret 只从服务端环境变量读取
- 服务端限制单次 JSON 请求不超过 1 MB

## 本地运行

```bash
npm install
npm run dev
```

不登录也可体验完整主链路：打开首页 →「使用示例文章体验」→ 阅读内置长文 → 浏览讨论瞬间 → 投票 → 进入讨论空间。

需要联调知乎登录或收藏时，先复制 `.env.example` 为 `.env`，填写赛事页面分配的配置：

```bash
cp .env.example .env
```

真实凭证只能保存在本地 `.env` 或部署平台 Secret 中，不能提交到 Git。AI Key 和知乎 Access Secret 都只配置在服务端；前端不得使用 `VITE_` 前缀暴露这些变量。

## 部署

### GitHub Pages（UI 预览）

**https://chelsealeezc.github.io/ZhihuWHY/**

源码只在 `main`。推送到 `main` 后，GitHub Actions 会自动构建并部署；不需要再维护 `gh-pages` 分支。Pages 设置里 Source 请选 **GitHub Actions**（不要选 Deploy from a branch）。

GitHub Pages 版本用于不依赖服务端密钥的界面演示。

### Vercel（完整 Demo）

Vercel 同时部署 Vite 前端与根目录 `api/` 下的 Functions。导入 GitHub 仓库后，在 Vercel 项目设置中配置 `.env.example` 列出的服务端环境变量；`SESSION_SECRET` 至少使用 32 个随机字符。

生产 OAuth 回调地址为：

```text
https://<你的-vercel-域名>/api/auth/callback
```

知乎部分 OAuth 环境不会在回调中返回 `state`。当前实现默认拒绝缺失 `state` 的回调；如需兼容，可在 Vercel 显式设置 `ZHIHU_OAUTH_ALLOW_MISSING_STATE=true`。

GitHub Pages 的 workflow 会单独设置 `/ZhihuWHY/` 基础路径，不影响 Vercel 根路径部署。

## 与知乎社区生态的契合

1. **有来路的真实表达是回响的基础** — 知乎回答的价值常常不只在结论，也在作者为什么这样判断、经历了什么、条件是什么。回响连接的不是抽象标签，而是带有作者、语境和原文出处的具体表达。

2. **同一场讨论天然分散在不同页面** — 知乎按问题组织内容，同一个议题可能出现在许多问题、回答和文章中。见解为这些内容增加一层更细的连接。

3. **用户的选择让内容关系变得可见** — 用户提交当前立场后，系统展示相近、不同和立场不明内容并说明判断依据，让用户有意识地寻找共鸣或理解分歧。

4. **从内容共鸣走向人与人的连接** — 回响先让双方因为某条具体表达相遇，用户已经知道对方讨论过什么、彼此在哪些地方相近或不同，再带着真实问题进入作者主页或私聊。

5. **旧内容与长尾内容获得新的流动路径** — 内容是否进入讨论取决于它能否回应当前问题，而非发布时间或原问题热度。匿名公开搜索让新用户无需先整理收藏即可进入流程。

6. **每一次发现最终回到知乎原文** — 相关内容始终保留作者、标题、片段和知乎原文链接。AI 只负责整理讨论和解释内容关系，不把站内内容改写成脱离来源的标准答案。
